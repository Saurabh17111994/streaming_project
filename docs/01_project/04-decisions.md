# Architectural Decisions

This file indexes active project decisions. Detailed implementation belongs in contracts, DDLs, and code. A revised decision explicitly supersedes older wording rather than leaving both active.

## Active decisions

| DEC-001 | Fluss is the live streaming bus and storage layer. LOG tables hold immutable events; KV tables hold current operational state.                                                                                                                 | One data plane and native changelog consumption.                                                                                                    | Requires strict table and column ownership.                                                               |
| DEC-002 | Flink performs candle computation, signal detection, ranking, and babysitting.                                                                                                                                                                 | Stateful event-time processing and checkpointed recovery.                                                                                           | Operational complexity is higher than stateless services.                                                 |

| DEC-005 | KV tables use explicit writer/column ownership and `partial_update` where supported.                                                                                                                                                           | Prevents unrelated column clobbering.                                                                                                               | Does not guarantee external exactly-once behavior or solve stale writes within one owner.                 |

| DEC-013 | Order lifecycle and position lifecycle are separate aggregates.                                                                                                                                                                                | A filled order is not equivalent to a closed position.                                                                                              | Babysitting operates on position state derived from fills.                                                |
| DEC-014 | Ingestion preserves original broker packet bytes plus normalized typed fields; canonical JSON cannot replace the original bytes.                                                                                                               | Supports replay and protocol evolution.                                                                                                             | Increases raw storage and requires payload redaction/access controls.                                     |
| DEC-015 | Broker tick and postback sequence IDs are unavailable until evidence proves otherwise. Tick and postback duplicate handling uses versioned bounded fingerprints and explicit limitations.                                                      | Avoids false exactness.                                                                                                                             | Logical duplicates may remain and identical legitimate events may be collapsed in bounded projections.    |
| DEC-016 | Instructions are immutable. Executor stores gate, attempts, identity mappings, and immutable execution audit in dedicated Fluss state and never mutates strategy fields.                                                                       | Makes crash-window reconciliation and ownership explicit.                                                                                           | Adds state tables and projection/recovery work.                                                           |
| DEC-017 | Position state is a separate fill-derived aggregate keyed by `position_id` and grouped by `trade_context_id`; MVP Babysitter is a strict no-op.                                                                                                | Prevents order/position conflation.                                                                                                                 | Real position actions require a later structured-action contract.                                         |
| DEC-018 | Production Flink checkpoints/savepoints use encrypted S3; Fluss LOG tables use three-node replication across workload VMs (KV tables are single-replica in Fluss 0.9.1 — durability via Fluss remote storage + rebuild from audit; **the "via Flink checkpoints" arm is SUPERSEDED for Signal business state by DEC-038** — Flink checkpoints are the durability mechanism only for Flink's small working/recovery state, never a second full copy of Fluss-owned business state); eligible live source tables retain at least three complete trading days and extend retention while EOD offload is unverified. | Supports one-VM tolerance and safe EOD retries. | Increases storage and operational cost. |
| DEC-019 | Resume from order safe-halt requires reconciliation and two distinct authenticated operator approvals for the same gate epoch/evidence hash.                                                                                                   | Reduces unsafe unilateral resume.                                                                                                                   | Increases operational response time.                                                                      |
| DEC-020 | Money-moving execution, gate, order, fill, mapping, approval, and action audit is encrypted and retained for seven years.                                                                                                                      | Supports live-money auditability.                                                                                                                   | Requires access control, lifecycle governance, and storage cost.                                          |

Arrow protocol evidence is available from the Go SDK and REST API docs.                                                         | Avoids compatibility work for stale undeployed schemas. These exact versions unblock DDL finalization.                                                       | None. Action Capture reconnection, replay, and in-band heartbeat behavior require Level 3 testing. | Sandbox order round-trip test (Level 3) required to close RISK-002 before live money. |

These endpoints provide near-real-time data for the two-person gate resume protocol (DEC-019). | Consistency delay, pagination, and rate limits (10 req/sec) are documented at Level 1; runtime reconciliation behavior requires Level 3 sandbox testing before live money. |
| DEC-024 | The active instrument manifest is fixed at 3,000 instruments per trading session. Runtime manifest changes require a controlled restart. Market-data arrival is variable: the expected baseline is 50,000 ticks/s on average (≈16.7/instrument), each instrument is capped at 30 ticks/s, and capacity is tested at the 50,000 ticks/s gate (the 90,000 ticks/s peak campaign was retired by DEC-036). | Separates expected-rate latency evidence from peak-capacity safety evidence without inventing a fixed arrival interval. | Instrument count changes between sessions require a controlled restart, not hot-reload. |
| DEC-025 | Production uses four cloud VMs: three workload/HA VMs (Flink + Fluss) and one dedicated OpenObserve VM. Each VM has a 500 GB SSD starting allocation. Final CPU, RAM, disk I/O, and network specifications are evidence-gated by `PERF-PROD-60000-001`. | Defines the deployment topology unambiguously. Machine sizing is deliberately evidence-gated rather than guessed. | 500 GB SSD is a starting point, not a proven sizing result. Co-located Flink/Fluss on shared VMs requires observability of resource contention. |
| DEC-026 | Fluss local retention is at most seven complete trading days, subject to measured capacity and the existing invariant that data SHALL NOT expire while EOD offload is unverified. S3 availability is not assumed; EOD failure retains data locally, retries offload, alerts operators, and prevents premature expiry. | Provides a concrete retention ceiling while preserving the stronger safety invariant. Avoids silent expiry during S3 outage. | Increases storage and operational cost. Seven-day capacity must be measured (`STOR-7DAY-60000-001`). |
| DEC-027 | Slow-Fluss policy is resolved by capacity: Fluss ingests up to 1-2 million ticks/s and the platform’s theoretical per-instrument-cap ceiling is 90,000 ticks/s (3,000 × 30; sustained gate 50,000 per DEC-036), so neither a durable local SSD buffer nor a controlled subscription pause is required. Bounded pending-append limits (50,000 records / min(64MiB, 10% container memory) bytes) remain as the defensive backpressure bound; indefinite in-memory buffering and silent data loss remain prohibited. | Fluss capacity (1-2M tps) exceeds the platform’s theoretical ceiling (90K tps; 50K gate) with margin, so no buffer or pause mechanism is needed. | Reaching a pending limit is a platform-capacity fault, not a normal operating condition; readiness halts until the bound recovers. |
| DEC-028 | Per-instrument freshness uses `FRESH`, `STALE`, `UNKNOWN`, and `MARKET_CLOSED` states. A `STALE` or `UNKNOWN` instrument halts decisions and orders for that instrument only — not unrelated healthy instruments. The exact freshness signal and threshold are evidence-gated (`EVIDENCE-GATE-FRESHNESS-001`). | Prevents a bad instrument from halting the entire platform while ensuring stale data never creates a new decision. | Requires per-instrument freshness tracking and scoped halt infrastructure. The numeric threshold is deferred until evidence is available. |
| DEC-029 | The single end-to-end latency release target is p99 < 100 ms trigger-tick-to-winner-commit at 50,000 ticks/s (3,000 instruments). Internal stage timings are diagnostic only — not independent release gates. | One clear pass/fail target for release decisions. Internal timings exist for diagnosis but do not multiply the release criteria. | The 100 ms target at 50K/s is asserted; it must be proven by `PERF-PROD-60000-001`. |
| DEC-030 | Broker connection recovery may take up to 5 minutes. This does not override per-instrument freshness: affected instruments halt as soon as they become stale. An Arrow REST request without a verified response after 15 seconds becomes an UNKNOWN outcome and halts all new orders globally. | Distinguishes slow reconnection from unsafe stale trading. Provides a concrete timeout for broker REST calls. | A 15-second timeout before halting all orders is conservative; it trades throughput for safety. |
| DEC-031 | Data-path services MAY auto-recover. Executor MAY auto-resume after restart ONLY when all seven safety proofs are present (known gate, valid fencing, no UNKNOWN attempts, no unresolved correlations, healthy changelog, healthy Signal checkpoints, fresh health signals). Missing any proof → remains HALTED; two-person reconciliation applies. | Allows clean restart to auto-resume when provably safe, while retaining fail-closed behavior for any uncertainty. Most restarts will still fall through to HALTED in practice. | The seven-condition proof is stringent; in practice most restarts will require manual reconciliation. |
| DEC-032 | Production runs a 3-node ZooKeeper ensemble (`zookeeper:3.9.2`), one member per workload VM, quorum 2-of-3. It serves (a) Fluss metadata/coordination — required by Fluss 0.9.1-incubating, whose official docs mandate a replicated ZooKeeper for production — and (b) Flink JobManager HA via `high-availability.type: zookeeper` using the same quorum, with HA metadata in the encrypted S3 checkpoint store. Dev Compose keeps single-node ZooKeeper. | A single ZooKeeper node is a single point of failure for the entire Fluss metadata layer; Fluss's own deployment docs prescribe a replicated ensemble for production. One trio serves both Fluss and Flink, matching the three-workload-VM topology. | Fluss plans to replace ZooKeeper with KvStore+Raft in a future release (roadmap); the ensemble then serves Flink HA only. Flink HA config adds a standby JobManager and ZK leadership to the operational surface. |
| DEC-033 | Production Swarm deployment is config-driven: bootstrap on a single production-like VM first (non-HA, single-node ZooKeeper, Fluss replication factor 1), then scale to the three-workload-VM topology by configuration and node addition (ZooKeeper ensemble, Fluss replication ≥2, placement/anti-co-location constraints). Docker Compose remains dev-only, and the single-VM stage is never HA evidence. | Allows building and validating one VM now and scaling to three later by config, without inventing a third environment definition. | The single-VM stage is not HA; it must never be cited as quorum/replication evidence. |
| DEC-034 | Signal detection (Slice 2.1) ships an MVP placeholder rule — one-candle breakout: on each closed 15s candle, a signal fires only when the candle is bullish (`close > open`) AND closes strictly above the highest high of the previous 20 completed candles (`SIGNAL_LOOKBACK_CANDLES`, configurable, ≥2). Ranking/reservations/decisions are postponed: a fired signal is appended as an immutable `Signal_Candidates` KV record (`side`=BUY, `action`=ENTRY, `order_type`=MARKET, `quantity` config-driven default 1) and nothing else happens downstream; candidate lifecycle (max-one-active, supersession, expiry) is also postponed. The placeholder is replaceable by the user's own trading logic later via `rule_id`/`strategy_id`/`strategy_version` without pipeline changes. | Produces an execution-engine-ready candidate record now (engine punches orders with zero reasoning) while deferring scoring/ranking; signal count is bounded (far fewer than a naive bullish-candle rule). | The MVP rule is a building-phase placeholder, not a trading strategy; the trend filter (`close > mean of prev closes`) is mathematically implied by the breakout condition, so the lookback length is the frequency knob. |

| DEC-038 | STATE OWNERSHIP (2026-08-14): **Fluss is the authoritative durable hot-state layer for the Signal job's large business state; Flink owns only the small working state needed for active processing plus the minimal recovery/checkpoint state needed to restart safely.** Concretely: the fingerprint dedup set (the only large Flink-managed state today — measured ~1.74 GB RocksDB at 53k t/s, 1024 tokens, 2026-08-12 bench) moves to a new Fluss KV state table (authoritative, rebuildable from `raw_table_1` replay within the dedup TTL); Flink retains a bounded in-process working cache for dedup lookups plus source offsets, watermarks, window/lateness timers, in-flight window accumulators, and the signal-detection ring buffers. Design, DDL, code, and measured sizes land in later stages — this decision only fixes ownership. Ranking/reservation state is explicitly NOT part of this decision. |

## Event fingerprint decision

The canonical fingerprint includes stable normalized values available in the decoded packet:

```text
event_fingerprint = hash(
  connection_id,
  instrument_token,
  event_time,
  tick_type,
  price and quantity fields,
  depth fields present in the packet
)
```

The fingerprint algorithm, numeric canonicalization, field order, and TTL are versioned. The raw canonical payload is retained for audit. Two byte-equivalent market events inside the TTL may be collapsed; therefore the guarantee is best-effort, not exact.

Without a broker sequence number, the platform cannot calculate exact missing sequence ranges. It may report suspected discontinuities from connection drops, heartbeat gaps, exchange-time jumps, or feed-health signals.
