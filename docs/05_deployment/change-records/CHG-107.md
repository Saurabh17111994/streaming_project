# CHG-107 — CLOCK_OFFSET_LIMIT_MS enforcement wired into the live boot loop

`CLOCK_OFFSET_LIMIT_MS` was declared in the stack env and parsed into
`ServiceConfig.clock_offset_limit_ms`, and `DriftMonitor` (clockwatch.rs) +
`Runtime::enforce_clock_drift` existed with unit tests — but **nothing in the
live `main.rs` boot loop ever invoked them** (09-production-swarm.md row 5:
"zero references in `04_executor/src`"). This change arms the periodic drift
check in the running service so the config value actually enforces the
fail-closed clock-drift contract. No runtime/topology/DDL/state change.

## Change

1. **`main.rs` periodic drift enforcement** — the boot loop now arms a
   `DriftMonitor` from `runtime.config.clock_offset_limit_ms` (the parsed
   `CLOCK_OFFSET_LIMIT_MS`) with a `FixedOffsetSource(0)` in the offline slice
   (a real NTP/chrony source is a Workstream-D/prod concern behind the same
   `OffsetSource` trait). A `tokio::time::interval` (default 30s,
   `CLOCK_DRIFT_CHECK_INTERVAL_S` env) drives `runtime.enforce_clock_drift`:
   `|offset| > limit` or an unmeasurable probe → `safety_halt()` (fail-closed,
   approvals cleared); recovery only via the sanctioned reconcile → approval →
   enable path. The main loop was restructured into a `loop { select! }` so
   the drift branch is non-terminal (a drift halt halts the gate, the process
   keeps serving health).
2. **`bootstrap.rs` test** — ties the config value through the runtime helper:
   at-limit = `Within` (gate stays HALTED), beyond-limit = `Beyond`, failing
   source = `Unmeasurable` — all keep the gate fail-closed HALTED.
