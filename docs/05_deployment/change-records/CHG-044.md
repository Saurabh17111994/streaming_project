## Summary

This change moves the pure-JVM safety rules (Task 5) from "prerequisite models only" into a
durable, offline-proven protocol. Three independent pieces:

1. **Reconcile the gate/attempt transition matrix.** The pre-T5 `GateTransitionValidator`
   allowed `ACCEPTED → REJECTED` and terminal → `UNKNOWN` and `PREPARED → CANCELLED/UNKNOWN`
   while `AttemptRecord.TERMINAL_PHASES` / `InMemoryAttemptStore` treated terminal phases as
   final. T5 freezes ONE canonical matrix in `AttemptPhase.legalTargets()` /
   `GateState.legalTargets()` (the dossier "Attempt rules" and the single enablement path
   `HALTED → RECONCILING → APPROVAL_PENDING → ENABLED` plus safety halt). The validator, the
   attempt-store writer, and the Rust gate all derive from it, so no runtime task can start
   with two different meanings for the same transition.

2. **Durable gate/attempt owner, lease, and fence fields.** `Execution_Gate` (v3) gains
   `owner_instance_id`, `fence_token`, `fence_acquired_ts`, `lease_expires_ts`, `fence_lost_ts`,
   and `approved_evidence_hash`; `Execution_Attempts` (v3) gains `gate_fence_token` so every
   money-moving command carries a durable record of the exact gate epoch AND fence token it was
   authorized under (the dossier's "PREPARED (request hash + client ref + gate epoch + fence)").
   `epoch` remains the gate-generation value and is not a substitute for the fence token. The
   DDL, Java layout, ownership matrices, manifest checksums, and agreement tests are all pinned.

3. **The durable protocol + crash-window proof.** `ExecutionCommandGate` composes a durable
   `AttemptStore` + `GateStateStore` + `BridgeCaller`: checks gate epoch/fence/approvals, persists
   PREPARED before any bridge call, transitions to SUBMITTING only after durable acknowledgement,
   calls the bridge exactly once per attempt, classifies verified acceptance/rejection, and turns
   all ambiguity into a persisted UNKNOWN + halt + reconciliation requirement. The crash-window
   suite injects a crash at every window (before prepare, after prepare, after SUBMITTING, before
   bridge, during bridge, after bridge, after evidence) and asserts zero duplicate fake-broker
   orders across restart; a restart observing SUBMITTING or UNKNOWN halts rather than re-placing.

## Behavior corrections recorded here (intentional, T5)

- `ACCEPTED → REJECTED` is now **rejected** (ACCEPTED is terminal) — the pre-T5 validator/store
  conflict.
- Terminal phases (ACCEPTED/REJECTED/CANCELLED) can never become UNKNOWN.
- `PREPARED` exits only to SUBMITTING (no PREPARED → CANCELLED / UNKNOWN).
- `HALTED → APPROVAL_PENDING` and `APPROVAL_PENDING → RECONCILING` are rejected (they skip the
  only enablement path / silently regress instead of halting), matching the Rust gate.
- `UNKNOWN → ACCEPTED/REJECTED/CANCELLED` remains legal but only through explicit
  reconciliation (`resolveUnknown`), never auto-retry (DEC-011, DEC-030).

## Remaining T5 wiring (not closed by this change)

The durable `GateStateStore` / `AttemptStore` boundaries are defined and proven offline; the
Fluss-backed writers that persist `Execution_Gate` v3 / `Execution_Attempts` v3 in a live cluster,
the env-gated gateway Fluss integration, and the Rust fake-bridge crash-window orchestration port
remain for the final T5 wiring step. The reconciled matrix, the fenced DDL, and the offline
protocol are fixed and pinned in this change.
