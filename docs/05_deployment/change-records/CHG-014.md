## What landed

**Problem (the post-SIGTERM freeze, root-caused at last):** the test spawned the
service with `ProcessBuilder` pipes and drained stderr through a reader thread,
then SIGTERMed with `proc.destroy()` and polled the buffer for the final
`bridge loop ended` report. The report never arrived — the buffer froze the
moment `destroy()` ran, while the service's JSON log (the `JSON_FILE` file
appender, a separate fd) always contained the complete shutdown sequence. The
same symptom reproduced in a minimal Java harness, which printed the smoking
gun: `[reader] IOException: java.io.IOException: Stream closed`.

**Root cause (proven with a slow-exit probe):** on this JDK (17.0.19),
`Process.destroy()` closes the parent-side process input streams immediately —
`IOException("Stream closed")` — **while the child JVM is still alive and
running its shutdown hooks**. The probe spawned a JVM whose hook sleeps 5 s:
`destroy()` → reader got `Stream closed` at t+0 while `childAlive=true` until
t+5 s. So the test's stderr reader thread died at SIGTERM, and every console
line the service wrote during its graceful shutdown — including the final
`bridge loop ended` report — entered a pipe with no reader and was discarded.
Bash probes worked because `kill -TERM` does not close pipe read ends. The same
mechanism explains the service's own `arrow-bridge: stderr drain error: Stream
closed` line (its `bp.destroy()` on the bridge kills the bridge-stderr drain
thread the same way); the bridge's authoritative per-token counts still survive
in `ARROW_TICK_COUNTS_FILE`.

**Fix (test harness):** the service's stderr and stdout are now redirected to
files (`ProcessBuilder.Redirect`), and the poll loop reads appended bytes from
the stderr file (`FileLog`). Files are immune to `destroy()`'s pipe closing —
the service keeps writing its shutdown sequence to the file, so the final
report is reliably captured. The undrained-stdout latent hazard is gone too
(both streams are files under the JUnit `@TempDir`).

**Append-growth assertions (the parked ING-E2E-001 follow-up):** with
`ARROW_TICK_COUNTS=1` the bridge reports its cumulative emitted-tick total
every second (drained and re-logged by the service). The test now, after the
forced disconnect: polls for a **second** `subscription_ack state=ACTIVE` (the
in-process reconnect, epoch 2), waits for the reported tick total to grow past
the reconnect-time baseline, SIGTERMs, and asserts the service's final
`bridge loop ended (ticks=B, errors=E, restarts=R)` report shows `B > baseline`,
`E == 0`, `R == 0` — the reconnect epoch demonstrably appended ticks to Fluss.
`IngestionService` carries the supporting shutdown-ordering fix: the hook joins
the main thread (bounded) so the loop's final report is logged before the JVM
halts; the bridge rebuild adds the `ARROW_TICK_COUNTS` per-second report.
