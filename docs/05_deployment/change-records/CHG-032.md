## What happened

CHG-015 (pipe-preserving bridge SIGTERM — the final `arrow-tick-counts` report must be
drained from stderr after the shutdown signal) was proven by a live E2E re-run; its
cluster-free regression draft (`BridgeShutdownRegressionTest` + `BridgeShutdownDriver`,
ING-UNIT-023) lived only in a Freebuff-session WIP commit (`a980a33`, branch
`freebuff/…abe1ab28…`) that was never landed and was deleted on 2026-08-18 after confirming
its other 39 files were all superseded by CHG-008…CHG-017. This record revives the one piece
that never landed — the drain regression — reconciled with the landed M3 design.

## Why the reconciliation matters

The WIP draft required the **real Go binaries** (faketool + arrow-bridge, spawned as a
driver JVM subprocess against a fake broker). Since 2026-08-18 those binaries are untracked
build artifacts rebuilt by the E2E runner — a default-run test depending on them would break
fresh checkouts. The landed M3 tests (`BridgeCrashLoopE2ETest`, `ShutdownDeadlockTest`)
established the pattern the revived test follows instead:

- **Scripted fake bridge** (a generated `#!/bin/sh` with a TERM trap) replaces the real
  bridge — the service treats the bridge subprocess as opaque, so the stderr
  tick-count-report channel and the `kill -TERM` drain path are exercised identically.
- **In-process** — the real `runWithBridge` loop runs on a spawned thread; `shutdown()` is
  invoked via reflection (same as `ShutdownDeadlockTest`), which runs the real
  `signalBridge()` → `kill -TERM` → `waitFor` → stderr-drain join → journal write path.
- **No Fluss, no Go binaries, no gate** — default-run via the ING-DQ-010 no-op-sink seam.

## What the test proves (the CHG-015 regression)

The observed run log shows the exact property: `arrow-tick-counts: total=1` (periodic) →
`signaling arrow-bridge (SIGTERM) for final tick-count report` → `arrow-tick-counts:
total=99` (the fake bridge's final report, drained from stderr AFTER the signal because the
pipes stay open) → `bridge exited normally (code=0)` → `bridge loop ended` → one journal
entry. A regression of `signalBridge()` back to `Process.destroy()` would close the
parent-side pipes and fail the "final report after the signal" + "no stderr drain error"
assertions.
