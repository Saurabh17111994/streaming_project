## What landed

**Problem (the service-side analog of the CHG-014 harness fix):** the shutdown
hook signaled the bridge with `Process.destroy()`. On this JDK (17.0.19)
`destroy()` closes the parent-side process pipes immediately —
`IOException("Stream closed")` — while the child is still running. So the
bridge-stderr drain thread died before the bridge's final `arrow-tick-counts`
report (the stderr mirror of `reportTickCounts`) arrived, and the main loop
took the exception path (`ingestion: bridge process error`) instead of reading
the bridge's final `bridge_shutdown` NDJSON event. The authoritative per-token
shutdown count for ING-TCP-001 survived only in `ARROW_TICK_COUNTS_FILE`, and
the logs lost both the report and the clean unwind.

**Fix (`signalBridge`):** the hook now signals the bridge with
`kill -TERM <pid>` (POSIX), which leaves the pipes open — the bridge writes its
final report to stderr, drains, EOFs, and exits 0. Falls back to
`Process.destroy()` if `kill` is missing or fails. The 10 s forced
`destroyForcibly()` fallback is unchanged.

**Restart/exit-code guard:** `running` stays true until the bridge exits (the
ordering the shutdown comment requires), so a forced-kill fallback exit (137)
in that window would previously have been judged an unexpected crash. The loop
now treats any shutdown-begun exit as requested (`requested = exitCode == 0 ||
!running || shutdownStarted.get()`), and `bridgeRestartDecision` takes a
`shutdownInProgress` parameter — a shutdown-begun exit is never logged
`BRIDGE_CRASH` nor restarted (a mid-shutdown restart would spawn a fresh bridge
that gets orphaned when the JVM halts).

**Drain-tolerance:** `drainStderr` logs `Stream closed` at INFO (it is the
destroy() artifact, only reachable on the forced path now) and keeps WARN for
other errors (sanitized).
