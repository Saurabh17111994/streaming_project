## What changed

1. **UNKNOWN → HALT 15 s global timer + operator review (04_executor `http.rs`)** —
   the two UNKNOWN-outcome return sites (503, never-ack) now call
   `record_unknown_outcome()`: an idempotent one-shot `tokio::spawn` escalation task
   fires after `ServerState::UNKNOWN_ESCALATION = 15 s` from the first UNKNOWN;
   `escalate_unknown_review()` forces `gate = Halted` from any state, sets
   `operator_review_required = true`, and logs `tracing::error!`. The `Snapshot`
   gained `unknown_first_seen: Option<Instant>`, `unknown_escalation: Duration`,
   `operator_review_required: bool` (manual `Clone` impl preserved), `/healthz`
   exposes `operator_review_required`, and `with_unknown_escalation(Duration)` is a
   test-only builder. Honest boundary: the watchdog operates on the route-level
   Snapshot (the surface harness-direct posts traverse); the executiongate.rs
   durable gate machine is not involved.

2. **Cancel command mapping (04_executor `intent.rs` + `http.rs` + `events.rs`)** —
   `cancel_envelope_from_payload(payload)` requires `instruction_id` + `broker_order_id`
   (missing → `Err("broker_order_id required for cancel")`), mints a fresh UUID v4
   attempt id and the same deterministic 14-hex `sha256("v1|ins|att")` ref as place,
   no order block, then `envelope.validate()`. `http.rs` dispatches on an optional
   `action` field: absent → "place" (back-compatible), `"cancel"` → cancel mapper,
   anything else → 422 `unsupported action`. `events.rs` derives
   `verification_evidence` from `place.command()` (`sync-cancel-ack` vs
   `sync-place-ack`) and defaults `order_status`-less acks per leg (`CANCELED` vs
   `ACCEPTED`, pendingQty 0). Accidentally-dropped `"verificationState": "VERIFIED"`
   restored.

3. **Config-profile doc truth (05-execution-core.md)** — `FENCING_LEASE_PROFILE` is
   already PINNED to `30s` in `config.rs:7` and the doc was updated (no longer
   TO_BE_DEFINED). `CHECKPOINT_PROFILE_ID` and `POSITION_ACTIONS_SCHEMA_VERSION`
   stay deliberately TO_BE_DEFINED: `CHECKPOINT_PROFILE_ID` has ZERO consumers
   (babysitter.rs is a NoOp MVP, no checkpoint/profile references) — pinning an
   unread constant would be weightless code. 05-execution-core.md:532/539 updated
   to say so.

4. **Projection backlog flood soak (06_execution_gateway)** —
   `GatewayConfig` gained `maxPendingProjectionRecords` (19-arg canonical ctor +
   legacy 18-arg delegating ctor, `DEFAULT = 1000`, validation
   `<= 0 → IllegalArgumentException("MAX_PENDING_PROJECTION_RECORDS must be positive")`,
   `fromEnvironment` tolerant of an absent env var — falls back to the default).
   `GatewayHttpServer` gained `projectionInFlight` (`AtomicInteger`) and a settable
   executor; the `/v1/events` handler now applies an in-flight bound: past
   `maxPending` → `readiness.durableWrites(false, "projection backlog N > M")` +
   503 (shed, no unbounded queue); restore only on FULL drain
   (`decrementAndGet() == 0` and currently not-ready → `"projection backlog drained"`),
   so the gateway stays conservatively not-ready while any apply is in flight past
   a flagged bound. `ProjectionBacklogFloodSoakTest` floods 16 signed concurrent
   EXECUTION_EVENTs at a blocked consumer with `maxPending = 4`: exactly 4×202,
   12×503, consumption concurrency peaks at the bound, readiness flips false
   mid-flood, restores after drain, a follow-up post returns 202 again.
