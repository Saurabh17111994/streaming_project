## What changed

The ENABLED `/v1/intents` SUCCESS path now additionally emits a normalized event image
to the gateway's `/v1/events` intake:

1. **`src/events.rs` (new)** — `lifecycle_event_value`: maps the synchronous bridge place
   report (broker id, ref echo) + the minted place envelope into an exact
   `NormalizedExecutionEvent` JSON — Java `06_execution_gateway` record shape
   (`postbackEventId/accountScopeId/executionPartitionId/gateEpoch/actorId/eventType/
   eventTs/audit/fill/lifecycle/position/correlation`, camelCase Jackson names;
   `audit`/`fill`/`position` = null — a synchronous place ack has no fill or position
   change). `postbackEventId` is deterministic per attempt (`pb-` + sha256 of
   `v1|instruction|attempt`) = gateway-ledger idempotency key; `lifecycle` carries
   broker id/instruction/attempt/trade-context/normalized-state/pending-qty/
   correlationState=VERIFIED; `correlation` carries ref/broker id/verificationState
   VERIFIED with evidence `sync-place-ack`. `emit_event`: envelopes it
   (gateway_protocol canonical, shared secret) and POSTs `{GATEWAY_ENDPOINT}/v1/events`;
   2xx = success; empty endpoint → Err (fail-closed).

2. **`src/http.rs`** — `Snapshot.gateway_endpoint` + `ServerState::with_gateway_endpoint`;
   SUCCESS branch: endpoint empty → `event_emission: "disabled"` (offline/paper mode,
   distinct from failure); otherwise attempt emission → `"accepted"` or
   `"failed:<reason>"`. **The order ack (202) is never changed by emission failure** —
   the order was already accepted by the bridge; failures are surfaced for the A2.4
   assertion to observe. No in-process retry: re-emission is ledger-idempotent by
   postback id (retries are the reconciler's job).

3. **`src/main.rs`** — `config.gateway_endpoint` (existing `GATEWAY_ENDPOINT` env, already
   in compose `http://execution-gateway:9180`) into the state; no compose change needed.

4. **`src/bridge/transport.rs`** — `HttpResponse` + `http_post` → `pub(crate)` (reused by
   the emitter; loopback only, same http_post the bridge client uses).

## Why this way

- The gateway's `/v1/events` intake (`GatewayHttpServer.events` → `ExecutionGatewayMain`
  `mapper.treeToValue(payload, NormalizedExecutionEvent.class)` → `FlussProjectionWriter`)
  owns the `Order_Lifecycle`/`Order_Correlation`/`Fills`/`Positions` writes; the Rust side
  supplies the normalized image. This matches the WP-4 "gateway owns projections, nautilus
  emits normalized images" split.
- The event is derived from the **synchronous** place report (not the WS postback): the
  route's forward is a separate transport instance and the LiveNode client never saw this
  order, so its postback correlation (`client_refs`) cannot attribute any eventual fill
  to it — the WS/fill leg (A3) needs the kernel-ingress design and stays open.
- `actorId "nautilus"`, `eventType "LIFECYCLE"` match the Java test fixtures
  (`ProjectionApplier`/`FlussProjectionWriterIntegrationTest` expectations).

## Honest boundaries (unchanged from CHG-090)

- `Execution_Attempts` KV: the harness A2 path posts directly to nautilus, so the Java
  `DurableIntentDispatcher` (which writes attempts) is not in that path; a durable
  attempt write for the route needs the B7.5 flag decision (Rust `FlussAttemptStore`
  path, default OFF) — **open**. A2.4's attempt-table assert stays gated on that.
- Fill/position legs (A3) + cancel leg (A2.4's cancel assert needs the cancel command
  path — `Command::Modify`/`Cancel` mapping is trivial extension of `intent.rs` but is
  not part of this change).
- Gate stays HALTED; while HALTED nothing is forwarded or emitted.
