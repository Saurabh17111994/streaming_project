## Summary

Completed pass — closes WP-3. The Fluss-backed `GateStateStore` (fence/lease/ownership + two-person approval) and
`AttemptStore` (exactly-one PREPARED) writers were already shipped (commit `68e46f8` under
CHG-044/045 wiring) but had **no durable (live-Fluss) verification**. This change adds the missing
env-gated integration drill that proves the durable-store guarantees against a real Fluss cluster,
with scratch tables created and dropped.

## What changed

- **Fluss writers (confirm, already shipped):** `FlussGateStateStore` delegates the protocol to
  `InMemoryGateStateStore` (the writes a raw KV upsert must never be trusted to provide:
  monotonic fences, distinct two-person approvals, exactly-once halt epoch) and persists each
  applied write to the v3 `Execution_Gate` table via `UpsertWriter`; `read()` falls back to a
  Fluss `Lookuper` when not cached. `FlussAttemptStore` does the same for `Execution_Attempts`
  (v3, `gate_fence_token` persisted at PREPARED).
- **Added `FlussGateAttemptStoresIntegrationTest`** (`@Tag("integration")`, gated on
  `FLUSS_BOOTSTRAP` like the Positions drill). Scratch Gate/Attempts tables are built from the
  `ExecutionGateColumns` / `ExecutionAttemptsColumns` ownership constants (themselves pinned to the
  v3 DDL by agreement tests), so the drill can never drift from the pinned layout. Proves, via
  **raw Fluss lookup** (independent of the store's in-process delegate):
  - gate boots `HALTED`, epoch 0, durably;
  - fence `acquire()` → monotonic token 1 + owner persisted;
  - two-person approval (op-a, op-b, same evidence hash) persisted;
  - **PREPARED-before-bridge** — `prepare()` row found in Fluss with `PHASE=PREPARED` and
    `gate_fence_token` persisted;
  - **exactly-one command** — re-prepare same `(instruction_id, request_hash)` → `DUPLICATE`,
    delegate still holds exactly one row.
- **20-plan** WP-3 marked DONE with evidence.

## What did NOT change

- No change to the InMemory stores — retained for offline unit tests (still green).
- Cross-restart (crash-window) zero-duplicate after a restart is enforced by the command gate's
  **reconciliation**, which reads these durable rows to find SUBMITTING/UNKNOWN attempts before
  minting anything new (the babysitter path, WP-5). This drill proves the durable rows exist for
  that reconciliation to see; it does not make the store alone reject a re-prepare across restarts.
- The drill itself is **env-gated and NOT run in this environment** — no Fluss cluster was up on
  `localhost:9123`. It compiles clean and is correctly env-gated (contributes 0 when unset).

## Completion pass (2026-08-21) — glued + restart-refresh

A review correctly challenged the first pass as over-stated: the Fluss writers existed but had
**zero production callers** and **no restart-refresh** (a restarted process would re-mint a
duplicate PREPARED). Both are now closed:

- **Wiring** — `ExecutionGatewayMain` opens `FlussGateStateStore` + `FlussAttemptStore` from
  `GatewayConfig` (`EXECUTION_GATE_TABLE` / `EXECUTION_ATTEMPTS_TABLE`, shared Fluss client) inside
  the try-with-resources: fails fast at boot if the v3 DDL tables are absent/unreachable, drops the
  durable gate/attempt backplane into the live Fluss-connected process, and registers readiness.
  *(Constructing `ExecutionCommandGate` against these stores is the executor bridge order path
  (WP-2) — there is no production `BridgeCaller` yet, so it is not seeded with a fake.)*
- **Restart-refresh (hydration)** — new seams:
  - `InMemoryGateStateStore.hydrate(GateRow)` — installs a recovered row and **advances the local
    fence sequence to at least its token**, so the next acquire is strictly greater (monotonic
    across restart).
  - `InMemoryAttemptStore.hydrate(AttemptRecord)` — rebuilds identity + replay-key indexes.
  - `FlussGateStateStore.read()/init()` hydrate-if-absent by Fluss lookup (and `init` never
    re-initializes an already-fenced durable gate).
  - `FlussAttemptStore.prepare()/transition()/resolveUnknown()` hydrate-if-absent by the
    deterministic `execution_attempt_id`, so a restarted process returns `DUPLICATE` instead of
    minting a second PREPARED — the crash-window zero-duplicate, now on the durable store.

Files (completion): `InMemoryGateStateStore.java`, `InMemoryAttemptStore.java`,
`FlussGateStateStore.java`, `FlussAttemptStore.java` (all `code/common/.../schema/execution/`),
`ExecutionGatewayMain.java`, `InMemoryStoreHydrationTest.java` (new, offline),

### Known boundary (not silently hidden)

Devices the single-restart-authority case. **Concurrent two-process fencing** (two live executors
claiming the same partition) is the deployment leadership/fencing mechanism
(ASM-EXE-005 / REQ-EXE-012) and is **not** replaced here — the Fluss store hydrates its local
authority but does not CAS on the durable row between processes. That genuine distributed Fencing
remains the advertised deployment mechanism (WP-5 / deployment layer), not claimed here.
