## What landed

The compute image previously **baked the job jar** (compiled code inside the
image build via a maven stage). Every code change therefore required a
~3-minute image rebuild. This change adopts the **native Flink split**:

- **Image = platform only** (Flink base + `submit-jobs.sh` launcher). The
  maven build stage and jar `COPY` are removed — image builds drop to <1 s
  and only occur when the launcher/Dockerfile changes.
- **Jar = host artifact**, delivered two ways:
  - dev: compose volume-mount `code/02_services/02_compute/target/compute.jar`
    → `/opt/flink-jobs/compute.jar` (read-only) — a code change needs only
    `mvn package` + container restart, **no image rebuild**;
  - job updates: `make rollout-savepoint` (unchanged) submits the host jar at
    runtime and restores from savepoint.
- **CHG-101 staleness sources** for `compute` now list only the Dockerfile +
  launcher (job code deliberately excluded) — code changes no longer flag the
  image STALE.

## Why

The rebuild-per-code-change loop is an anti-pattern: the image is a packaging
layer, not the job artifact. Flink's native model is "submit the jar to a
running cluster"; the repo already had 90% of it (`rollout-savepoint`,
`submit-jobs.sh`). This completes the split so dev iteration is
`mvn package` (seconds), not image rebuilds (minutes).

## Guard (drift prevention)

`NativeSplitGuardTest` (4 assertions) fails if anyone re-bakes the jar into
the image: no `COPY 02_services` tree, no `RUN mvn`, no `COPY compute.jar`
in the Dockerfile; the compose service must mount the host jar; the staleness
source list must exclude the job source tree.
