## What landed

**Problem:** an unclean tablet shutdown left preallocated/zeroed tails past the last complete batch in 12 of raw_table_1's 16 log segments (today's E2E crash). The tablet crash-looped on recovery (`Failed to load record batch ... EOFException ... Expected to read 48 bytes, but reached end of file after reading N bytes`), and the E2E wasted the full 90 s startup window polling for `Fluss connected` before failing with a confusing stderr tail. Fluss's reported error position is not the true boundary — a zeroed batch header misparses as valid and the reader jumps through the garbage region — so the first "truncate 40 bytes" attempt merely exposed the next misread.

**Pre-flight (`FullStackE2ETest`):** before launching the service, the test verifies TCP 9123 (coordinator) and TCP 9124 (tablet) accept. The tablet only binds after *every* log segment recovers, so a missing tablet listener while the container crash-loops means truncated segments; the failure message names the repair tool. A stopped stack (both ports down) reports "start the dev stack" instead. Docker is only consulted for the diagnostic (best-effort, null-safe) — the gate itself is plain TCP.

**Repair tooling (`code/01_platform/04_scripts/fluss-repair/`):**
- `LogScan.py` — pure-Python segment scanner using the server's own batch arithmetic (`batchSize = 12 + int32_le(header[8:12])`, verified against `DefaultLogRecordBatch` and a known batch: bytes `24 09 00 00` = 2340); an all-zero 48-byte header marks the preallocated tail. Validated against the authoritative in-JVM scan of bucket 6 (both report `TRUNCATE_TO=670345400`).
- `repair-tablet.sh` — discovers the tablet container + data volume (prefers an active container over Exited ones from other compose projects), auto-detects the live `raw_table_1` table (id suffix changes on recreation), scans every segment, truncates each affected segment to the exact end of the last complete batch, restarts the tablet, and verifies recovery completed. `DRY_RUN=1` reports without touching anything; refuses to act while the tablet is Up (a healthy active segment is mid-append — a false-positive truncation must never race a live write). Only zeroed/never-written bytes are removed — no complete records lost.

**Verification:** the tool's live DRY_RUN scan of the repaired cluster reports 16/16 segments OK (each size matching the authoritative boundary from the repair), and the cluster re-verified 24/0/0 (`ddl-bootstrap: verified 24 tables ok, 0 missing, 0 schema-mismatch`). Full procedure + history documented in the ING-E2E-001 runbook section of 11-testing-and-release.md.
