## What changed

The `POST /v1/intents` ENABLED path in `code/02_services/04_executor/src/http.rs` no longer
acks-without-executing. With a bridge transport attached, a verified + gate-ENABLED intent is
mapped to a private bridge `place` command and forwarded; the synchronous report is mapped
back to the gateway response. No strategy/actor/node change: the LiveNode `!Send` + no-strategy
invariants are untouched (see §Scope).

### Code (all in `code/02_services/04_executor`)

1. **`src/intent.rs` (new)** — `place_envelope_from_payload`: verified gateway payload
   (BI-EQ sandbox schema: `instruction_id/symbol/exchange/side/quantity/order_type/
   limit_price_paise/product_type/time_in_force`) → bridge `CommandEnvelope` (place).
   Identity separation mirrors `BridgeExecutionClient::build_order_envelope` exactly:
   `execution_attempt_id` = fresh UUID v4 per attempt; `client_order_ref` = deterministic
   14-hex `sha256(v1|instruction|attempt)` via the now-`pub(crate)`
   `deterministic_client_order_ref` (05-execution-core §Reconciliation, fits Arrow
   16-char remarks). Enums map fail-closed: side BUY/SELL; order_type LIMIT/MARKET/
   SL-LIMIT/SL-MARKET; product CNC→Cash/MIS→Intraday/MTM→Monthly; TIF DAY/IOC. A
   MARKET payload never carries a price to the wire (protocol rejects priced MKT);
   LIMIT requires `limit_price_paise`. `envelope.validate()` runs before return — a
   half-mapped order can never be sent.

2. **`src/http.rs`** — `ServerState` gains `forwarder: Option<BridgeForwarder>` where
   `BridgeForwarder = Arc<tokio::sync::Mutex<Box<dyn BridgeClient + Send>>>` (Send bound is
   required by the spawned server task; the nautilus runtime still uses the non-Send
   `Box<dyn BridgeClient>` for its own client). `route` is now `async`. ENABLED flow:
   forwarder absent → paper 202 ack (offline/test construction, unchanged behavior);
   forwarder present → map payload (422 on mapping failure) → `send_command` single
   attempt → SUCCESS 202 (`accepted/broker_order_id/client_order_ref/execution_attempt_id/
   instruction_id/order_status/gate_state`), REJECTED 409 (`accepted:false,outcome:REJECTED`),
   UNKNOWN or transport error 503 (`outcome:UNKNOWN` — never an ack, never a retry; a lost
   ack is reconciled by query per the unknown-outcome contract). Auth 401 / HALTED 503
   paths unchanged and executed before any mapping/forward.

3. **`src/main.rs`** — `build_route_forwarder(&BridgeSelection)`: Fake selection → scripted
   `FakeBridge` (`CommandScript::Accept`), Http selection → `HttpBridgeClient`
   (`BRIDGE_ENDPOINT`/`BRIDGE_AUTH_TOKEN`, same credentials the node's exec client uses).
   Attached via `runtime.server_state().with_forwarder(...)`.

4. **`src/execution/client.rs`** — `deterministic_client_order_ref` visibility
   `pub(crate)` (rule unchanged; used by `intent.rs`).

## Scope / honest boundaries

- **Sync leg only.** The A2.4 lifecycle leg (bridge WS postback → normalized event →
  gateway `/v1/events` → `FlussProjectionWriter`) and the durable attempt-store flags
  (B7.5, default OFF) are NOT wired by this change. With the gate ENABLED, a real order
  reaches the bridge and gets a broker id, but `Order_Lifecycle`/`Execution_Attempts`
  rows are still written by the Java gateway path only. A2.4 remains open.
- **Gate stays HALTED** (`EXECUTION_ENABLED=false`): while HALTED the route returns 503
  before mapping/forwarding — the new code is behavior-neutral in the currently deployed
  profile (verified by `intents_halted_never_forward_is_bridge_untouched`).
- **LiveNode untouched**: no strategy, no kernel ingress; the node's own exec client
  (fill correlation/report intake) is not on this path. The route's `send_command` is a
  separate transport instance (same wire credentials), which is why the forward is
  explicitly scoped to the synchronous ack. Full order-lifecycle wiring (route → nautilus
  engine → registered exec client) remains the open question (kernel ingress surface or
  strategy/actor layer — needs a pinned-nautilus design decision; see plan Task A2 note).

## Decision notes

- `Mutex<Box<dyn BridgeClient + Send>>` (not the LiveNode's client) because `LiveNode` is
  `!Send` and `LiveNodeHandle` exposes only `state/stop/is_running` — there is no public
  submit-inchannel in pinned nautilus; verified by reading the pinned checkout
  (`crates/live/src/node/state.rs:116-128`, `node/mod.rs`).
- Deterministic ref reused (not re-minted differently) so a future report-correlation leg
  can join on the same 14-hex ref that postback `remarks` carries.
- 422 mapping failure (not 400): the envelope itself verified; the payload contract is
  violated. 409 rejection (not 422): the broker rejected a well-formed order — terminal.
- No auto-retry in the route: a transport error is UNKNOWN→503; retrying could duplicate
  the order (the durable attempt/fence story is the client path, out of scope here).
