# CHG-099 — EOD parallel bucket copy: drain-loop fix, 24k rows/s, large-table drill PASS

The 2026-08-24 live extend drill (CHG-098) exposed that the shadow-table
copy path was unusable for large tables: `performRewrite` awaited every
row's ack before the next (one RTT per row, ~9.6 rows/s measured ->
385k rows would take ~11 h). This change replaces the copy with a parallel
16-bucket rewrite and fixes a second, subtler correctness issue found while
measuring it (time-bounded `pollBatch` batches).

## What changed

1. **Parallel bucket copy** (`copyBucketsParallel` / `copyBucket`): one worker
   thread per bucket (capped `COPY_THREADS=16`), each with its own
   `UpsertWriter` and batched async acks (`COPY_WRITE_BATCH=500` futures per
   await). No new CLI surface; `extend --apply` behaves identically.
2. **Drain-loop fix** (`copyBucket`): the client's `BatchScanner.pollBatch`
   returns a *time-bounded* batch, not the whole bucket. Under 16-way
   concurrent scans the single-batch pattern measured a uniform ~6.8% sample
   of each bucket (26,099 of 385,389 rows; 68 of 1,078 tokens) — wrong rows
   copied silently, caught by the tool's own parity check, then root-caused
   by a dedicated probe. The copy now repeats `pollBatch` until null/empty;
   `pollBatch` may also return null (NPE caught in the probe), checked too.

## Flink batch-copy finding (design record, not implementation)

A Flink bounded batch copy job was prototyped and **rejected at design**: the
fluss-flink-2.2 connector's `FlussSourceBuilder` hardcodes `streaming=true`
and the FlussSource constructor is package-private; the public `FlinkSource`
12-arg constructor with `streaming=false` produces a `BOUNDED` source which
**requires `table.datalake.enabled=true`** — the enumerator aborts with
`UnsupportedOperationException: Batch only supports when table option
'table.datalake.enabled' is set to true.` The dev/drill tables are
lake-disabled by design, so the bounded Flink path cannot read them; the
raw-client parallel copy is the supported large-table path today. Revisit
only if lake-enabled tables enter the stack.

## Performance projections (honest)

- Measured: 385,389 rows → ~16 s total incl. shadow create + parity scans
  (~24k rows/s on this laptop/dev cluster).
- 1024 stocks × full day (≈1.54 M candle rows/day; ≈49 M rows at 32 d):
  linear scaling projection ≈ 33 s per ~1 M rows → ~30 min for 49 M rows on
  the same raw-client path (still bounded by per-bucket scan + batched
  upserts; a Flink sink path would add parallelism but needs a lake-enabled
  source — not available on lake-disabled tables).
