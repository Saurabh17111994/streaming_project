## What landed

**Problem:** the shutdown hook signals the bridge captured at the start of the
hook (`currentBridgeProcess`). A bridge the main loop restarted between that
read and `running=false` — a crash-restart racing the SIGTERM — is never
signaled: the loop exits on `running=false`, main dies, and the fresh bridge
keeps running after the JVM halts, emitting into a dead pipe forever. The test
harness also had no check that its own children (the fake broker) were gone.

**Fix — final orphan sweep in `shutdown()`:** after the main-thread join, the
hook re-reads `currentBridgeProcess`; if it differs from the already-signaled
process and is still alive, it is taken down (graceful `kill -TERM` via
`signalBridge`, 3 s wait, then `destroyForcibly`) so nothing survives the JVM
halt. Bounded (~3 s worst case); a no-op on the FATAL-startup path (no bridge).

**E2E assertions (ING-E2E-001):** after the service exits, the test parses the
last `arrow-bridge started (pid=N)` from the service log and asserts that pid
is no longer alive (`ProcessHandle.of(pid).isAlive()` — false when the process
is gone) — proving the hook reaped the bridge. The fake broker is
force-reaped in the `finally` and asserted dead (no orphaned broker survives
the test).

**Documented boundary:** the sweep runs inside the shutdown hook, so it cannot
fire when the JVM is SIGKILLed or crashes (no hook runs). The Go bridge's
parent-death detection (e.g. a PDEATHSIG/prctl-style watch) is the natural
follow-up for that case; the E2E assertion covers the graceful path.
